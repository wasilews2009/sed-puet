# СЕД ПУЕТ — застосунок (API + веб-інтерфейс)

Один FastAPI-застосунок, що збирає модулі проєкту під єдиним API і єдиною автентифікацією та
віддає веб-інтерфейс українською. Модулі-сусіди не змінювались: застосунок підключає їх як бібліотеки.

| Модуль | Що дає застосунку |
|---|---|
| `../db-schema` (`sed_db`) | моделі, міграції Alembic, тригери HITL і журналу аудиту |
| `../ingest-pipeline` (`sed_ingest`) | реєстрація файлу → MinIO → OCR → реквізити від локальної LLM з впевненістю |
| `../rag-compliance` (`sed_rag`) | нормативний аудит проєкту з цитатами пунктів (Qdrant + LangGraph) |
| `../approval-routing` (`sed_routing`) | маршрути погодження, візи, КЕП (CAdES), ключі користувачів |
| **`sed_app`** (тут) | JWT і 9 ролей, політика доступу (ABAC), реєстр і картка документа, ручна валідація, черги, веб-інтерфейс, docker-compose |

**Принцип:** ШІ лише асистент. Значення з впевненістю < 0.85 потрапляють у чергу ручної перевірки; навіть
упевнені значення переносить у картку людина (одним кліком). Юридичної сили документ набуває тільки
після КЕП посадової особи. Усе працює on-prem: LLM, ембединги, OCR, сховище, SSO.

## Швидкий старт (docker compose)

```bash
cd sed-app
cp .env.example .env                       # замініть усі CHANGE_ME
docker compose --profile gpu up -d --build # LLM на vLLM (NVIDIA GPU; для 24B потрібно ≈ 48 ГБ VRAM)
# або: docker compose --profile cpu up -d --build
#      docker compose exec llm-ollama ollama pull mistral-small3.1:24b   (і розкоментуйте Ollama-рядки в .env)
```

| Адреса | Що |
|---|---|
| http://localhost:8080 | веб-інтерфейс; API — `/api/v1`, Swagger — `/api/docs` |
| http://localhost:8180 | Keycloak (realm `puet`, адмін — `admin` / `KEYCLOAK_ADMIN_PASSWORD`) |
| http://localhost:9001 | консоль MinIO |

Сервіс `migrate` накочує міграції, DDL ключів КЕП з `approval-routing/schema_proposal` і (з `--demo`)
демо-дані: 8 підрозділів, 10 користувачів, шаблон маршруту службової записки на закупівлю.
Демо-користувачі в Keycloak: логіни `rector`, `vicerector`, `director`, `head.kknit`, `lecturer`, `student`,
`studgov`, `buh`, `pfv`, `clerk`, тимчасовий пароль `demo` (Keycloak попросить змінити).

Нормативний корпус індексується CLI модуля RAG усередині контейнера:
`docker compose exec app python -m sed_rag.ingestion.cli ingest-manifest /opt/sed/rag-compliance/corpus/manifest.toml`.

Порти БД, Qdrant, LLM і ембедингів назовні не публікуються; веб-порти прив'язані до `127.0.0.1` —
перед застосунком у production ставиться реверс-проксі з TLS.

### Без Docker (розробка)

```bash
pip install -r requirements.txt
export PYTHONPATH=.:../db-schema:../ingest-pipeline:../rag-compliance:../approval-routing
SED_DATABASE_URL=postgresql+psycopg://sed:***@localhost/sed python -m sed_app.cli.migrate --demo
SED_APP_ENVIRONMENT=development SED_APP_AUTH_MODE=dev SED_APP_DATABASE_URL=... \
  uvicorn sed_app.main:create_app --factory --port 8080
```

У режимі `auth_mode=dev` на сторінці входу є кнопки демо-користувачів (токени RS256 підписує сам застосунок).
У `environment=production` цей режим заборонено: застосунок не стартує.

Тести: `SED_TEST_DATABASE_URL=postgresql+psycopg://postgres:***@localhost/sed_app_test pytest` (потрібні
PostgreSQL 16 і pgvector; MinIO, Tesseract і LLM замінено фейками). Перевірка типів JS: `tsc -p sed_app/web/static/jsconfig.json`.

## Архітектура

```
 Браузер (ES-модулі, без збірки, CSP 'self')
    │  Authorization Code + PKCE (Keycloak)  /  dev-login
    ▼
 FastAPI  sed_app.main:create_app
    ├─ auth/        OIDC-перевірка JWT (JWKS) → AppPrincipal; ролі = ролі БД ∩ ролі токена
    ├─ domain/      політика доступу (чисті функції), нормалізація реквізитів, помилки, підписи
    ├─ adapters/    SQL-читання реєстру/картки з тим самим фільтром доступу, HITL-записи, MinIO
    ├─ api/         /auth, /me, /documents, /review-queue, /approvals/inbox, …
    ├─ sed_ingest   POST /documents/ingest        ─► MinIO ─► Tesseract ─► LLM (structured output)
    ├─ sed_rag      POST /documents/{id}/compliance-checks ─► Qdrant (dense+BM25) ─► LLM ─► зауваження з цитатами
    └─ sed_routing  /route-preview, /routes, /steps/{id}/decision|sign, /kep/*  ─► CAdES-перевірка КЕП
    ▼
 PostgreSQL 16 (pgvector): guard-тригери HITL, історія статусів, журнал аудиту з хеш-ланцюгом
```

Clean Architecture: `domain` не залежить від FastAPI і SQLAlchemy; `adapters` реалізують доступ до БД і
сховища; `api` — тонкий шар DTO (Pydantic) і залежностей. Модулі під'єднуються через їхні власні
`create_app(...).lifespan` і `dependency_overrides` (спільна автентифікація замість їхньої).

**Потік документа.** Реєстрація (файл → оригінал у MinIO з SSE → OCR → реквізити від LLM з впевненістю
по кожному полю) → ручна валідація (підтвердити / виправити / відхилити; впевнені — перенести разом) →
нормативний аудит (зауваження з цитатами пунктів актів; людина приймає або відхиляє кожне) →
маршрут погодження (типовий для виду документа і підрозділу; відкриті критичні зауваження блокують запуск,
якщо автор свідомо не підтвердив) → візи і КЕП по черзі → статус «Погоджено».

## Ролі і доступ

Ролей рівно 9 (рішення власника проєкту: без окремих «діловода» і «оператора перевірки ШІ»).
Ролі задаються в Keycloak (realm roles) і в `user_roles` з прив'язкою до підрозділу; діє їх перетин,
тож відкликання ролі в будь-якому з двох місць одразу забирає доступ.

| Роль | Бачить | Перевіряє результати ШІ | Запускає погодження |
|---|---|---|---|
| Ректор, проректор | усі документи | усі | будь-який документ |
| Директор інституту, завідувач кафедри, керівник підрозділу | свій підрозділ з дочірніми (усі грифи) | там само | там само |
| Викладач, співробітник | свій підрозділ: «Публічний», «Внутрішній»; свої документи | там само | лише свої |
| Студент, голова студентського самоврядування | «Публічні», свої, ті, де є учасником маршруту | лише свої | лише свої |

Учасник маршруту бачить документ, але не править реквізити чужого документа. Після погодження (і в інших
фінальних статусах) реквізити не змінюються. Документ, недоступний користувачеві, повертає 404, а не 403,
щоб не розкривати його існування. Нормативний корпус змінюють ректор і проректор
(`SED_RAG_CORPUS_ADMIN_ROLES`), чужі ключі КЕП відкликає ректор (`SED_ROUTING_KEP_ADMIN_ROLE`).

Та сама політика реалізована двічі: чистими функціями (картка, дії) і SQL-умовою (реєстр, черги).
Тест `test_visibility_matrix_matches_policy` перевіряє, що обидві дають однаковий результат для всіх 10 користувачів.

## Human-in-the-loop

* Поле з впевненістю < 0.85 має статус «Очікує перевірки» і потрапляє в чергу «Перевірка ШІ».
* Поле з впевненістю ≥ 0.85 — «Не потребує перевірки», але в картку (`documents.requisites`) його
  переносить людина кнопкою «Перенести в картку впевнені значення». Некоректні за форматом (напр. автор
  без ПІБ) пропускаються і лишаються для ручного виправлення.
* Будь-яке значення можна виправити («Виправити»), навіть уже підтверджене.
* Модель недоступна або нічого не вилучила → форма ручного введення реквізитів.
* Звіт нормативного аудиту приймається лише тоді, коли кожне зауваження розглянуто.
* Кожне рішення пише хто, коли і з яким коментарем; запис у БД іде від імені користувача
  (`sed.actor_type = user`), і guard-тригери не дозволять ШІ-воркеру змінити ці поля.
* Інтерфейс на кожній картці нагадує: реквізити і зауваження від ШІ юридичної сили не мають.

## Безпека: ризики і що зроблено

| Ризик | Захід |
|---|---|
| Підроблений або чужий токен | перевірка підпису за JWKS, `iss`, `aud=sed-api`, `exp`, допуск годинника 30 с; ролі — перетин БД і токена |
| Dev-вхід у production | `auth_mode=dev` і імітаційний КНЕДП забороняються валідаторами налаштувань у production |
| Перебір ідентифікаторів документів | 404 для недоступних; доступ перевіряється на кожному запиті до картки, файлу і дій |
| XSS у даних з OCR / LLM | інтерфейс не використовує `innerHTML`; CSP `script-src 'self'`, `style-src 'self'`, `frame-ancestors 'none'` |
| Prompt injection у тексті документа | модель лише пропонує значення; структурований вихід за JSON Schema; людина підтверджує; ШІ не має прав на юридично значущі поля в БД |
| Витік ПД у моделі і журнали | LLM локальна; модуль інжесту псевдонімізує ПД перед моделлю; документ з ПД отримує гриф «Персональні дані» автоматично |
| Підміна підпису КЕП | CAdES-перевірка: ланцюг до довірених КНЕДП, OCSP, хеш саме цієї версії, власник сертифіката = призначений учасник |
| Одночасне редагування картки | `row_version` → 409 і перезавантаження картки |
| Втручання в журнал | хеш-ланцюг `audit_logs`, перевірка `sed_audit_verify()`; перегляд картки і завантаження файлу записуються як події |
| Кешування відповідей API | `Cache-Control: no-store` на `/api/*` |
| Контейнер | непривілейований користувач, `read_only`, `cap_drop: ALL`, `no-new-privileges` |

**Відкриті ризики (до production):**
1. Один користувач БД на весь застосунок. Ролі `sed_app` і `sed_ai_worker` з `../db-schema/roles.sql` слід
   розвести: синхронний інжест зараз пише результати ШІ тим самим пулом, що й дії людей.
2. Виклики LLM синхронні в HTTP-запиті (реєстрація до кількох хвилин). Потрібна черга (Arq/Celery) і воркер з роллю `sed_ai_worker`.
3. Keycloak у compose — dev-режим з H2; у production — університетський Keycloak з TLS і MFA для ректорату.
4. Імітаційний КНЕДП увімкнено в `.env.example` для стенду; для реальних підписів потрібні сертифікати
   КНЕДП з Довірчого списку (`SED_ROUTING_KEP_TRUST_ANCHORS_PEM`) і, для ДСТУ 4145, сервіс перевірки (`SED_ROUTING_KEP_DSTU_VERIFIER_URL`).
5. Демо-паролі `demo` і демо-дані — лише для стенду (`SED_MIGRATE_FLAGS=` у production).

## Крайні випадки

* **Скан без тексту / модель впала** — документ реєструється, реквізити вводяться вручну, запуск NER закривається як «Виправлено».
* **Дублікат файлу** — інжест повертає посилання на раніше зареєстрований документ.
* **Нова версія документа** — рішення по полях прив'язані до версії; поле не поточної версії не правиться (409).
* **Користувач є в Keycloak, але не в БД** — створюється без ролей (бачить лише публічне), поки адміністратор не призначить роль.
* **Роль відкликано в Keycloak** — діє одразу з наступним токеном, навіть якщо в БД вона лишилась.
* **Критичні зауваження аудиту відкриті** — маршрут не запускається без явного підтвердження автора (фіксується в журналі).
* **Учасника маршруту немає на посаді** — крок пропускається або заміщується, що видно в попередньому перегляді маршруту.
* **Qdrant або LLM недоступні** — застосунок стартує, `/readyz` показує стан, дія повертає 503 з поясненням.
* **Підпис чужим ключем** — відхиляється (тест `test_signature_of_another_person_is_rejected`).

## Що потрібно від модулів

Ці зміни застосунок обходить, але їх варто внести власникам модулів:

1. **rag-compliance:** маршрут `POST /api/v1/documents/versions/{version_id}/compliance-checks` має власну перевірку доступу,
   ширшу за політику застосунку. Застосунок його приховує і дає свій
   `POST /documents/{id}/compliance-checks` (поточна версія, перевірка `can_review`). Варто приймати функцію доступу ззовні.
2. **rag-compliance:** типова роль адміністратора корпусу `sed-regulations-admin` не входить до 9 ролей; у compose задано `["rector","vice_rector"]`. Варто змінити типове значення.
3. **approval-routing:** `kep_admin_role = "sed-kep-admin"` і `ai_service_roles = {"sed-ai-service"}` також поза 9 ролями; у compose — `rector`.
4. **approval-routing:** `schema_proposal/0003_kep_keys.sql` ще не в міграціях `db-schema`; поки його накочує `sed_app.cli.migrate`.
5. **approval-routing:** назви кроків (`title_uk`) беруться з TOML-шаблону і не зберігаються в БД — картка
   отримує їх окремим запитом до `/documents/{id}/route`. Краще мати колонку в `approval_steps`.
6. **approval-routing:** `Caller.roles` будується з ролей токена; застосунок передає їх як є. Варто брати ефективні ролі (перетин з БД).
7. **Усі модулі:** кожен створює власний пул з'єднань (застосунок + routing + rag ≈ 3 пули на процес). Варто
   приймати `async_sessionmaker` ззовні.
8. **ingest-pipeline:** не заповнює `documents.requisites` для впевнених полів (це правильно для HITL), але
   й не позначає, що їх потрібно перенести; застосунок робить це окремою дією людини (`requisites/accept-confident`).
9. **Усі модулі:** синхронні виклики LLM у HTTP-запиті → черга завдань і окремий воркер (див. ризик 2).

## Перевірено

* 35 тестів на PostgreSQL 16 + pgvector (реєстрація, ручна валідація, ручне введення, матриця видимості для 10 користувачів,
  аудит завантаження, комплаєнс, наскрізний маршрут з 5 підписами, повернення на доопрацювання, чужий підпис, заголовки безпеки).
* Браузер Chromium (Playwright): викладач реєструє службову записку → картка → маршрут → 5 учасників по черзі
  погоджують з імітаційною КЕП → «Погоджено», 5 чинних підписів; студент отримує 404.
* `tsc --strict` для JS інтерфейсу; `docker compose config` валідний.
* Образи Docker у цьому середовищі **не збирались** (немає Docker-демона): збірку і запуск compose треба перевірити на сервері.
