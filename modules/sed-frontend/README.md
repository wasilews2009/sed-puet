# СЕД ПУЕТ — веб-інтерфейс (Frontend Reviewer)

Окремий односторінковий застосунок (React 18 + TypeScript + Vite + TailwindCSS), що працює через API
`../sed-app` і не змінює його код. Інтерфейс українською, навігація залежить від ролей, доступність — WCAG 2.1 AA
(перевіряється axe у наскрізних тестах).

**Принцип, якого дотримується кожен екран:** ШІ лише пропонує. Значення з впевненістю < 0.85 позначені і стоять у
черзі «Перевірка ШІ»; навіть упевнені значення переносить у картку людина; юридичної сили документ набуває лише після
КЕП посадової особи. Інтерфейс показує впевненість біля кожного значення і нагадує про це на картці й у підвалі.

## Підпис КЕП у браузері і точки розширення

Сервер приймає відокремлений CAdES над SHA-256 версії документа (або виклику при закріпленні). У `src/kep/`:

```
 signing-request (SHA-256, прийнятні рівні)            challenge (дані, SHA-256, строк)
            │                                                  │
            ▼                                                  ▼
   SignaturePicker ── засоби (KepSigner) ───────────────────────────────────────────┐
     ├─ file   : .p7s з «ІІТ Користувач ЦСК», Дія.Підпис, ПриватБанк (будь-який КНЕДП) │
     ├─ pkcs12 : .p12/.pfx (ECDSA/RSA) → pkcs12.ts (WebCrypto, ключ неекспортований)  │
     │           → cades.ts (CAdES-BES: content-type, signing-time, message-digest,    │
     │             signing-certificate-v2; DER-сортування SET OF)                       │
     ├─ mock   : імітаційний КНЕДП стенду (лише якщо бекенд його ввімкнув)              │
     └─ registerSigner({id:"iit", sign}) — адаптер бібліотеки ІІТ для ДСТУ 4145 ─────────┘
            │  base64(.p7s)
            ▼
   POST /steps/{id}/sign  або  POST /kep/keys  → серверна перевірка (ланцюжок, OCSP/CRL, власник)
```

* Пароль і особистий ключ не залишають браузер; після підпису пароль стирається з форми.
* Контейнер, зібраний у браузері, перевіряється серверним `CadesVerifier` у тесті `src/kep/cades.node.test.ts`
  (через `keytool verify` модуля маршрутів) і в наскрізному тесті (віза зав. кафедри внутрішнім ключем).
* Ключі ДСТУ 4145 (Key-6.dat, .jks ПриватБанку) браузер без бібліотеки ІІТ не відкриє: зараз — через файл підпису;
  для підпису в браузері зареєструйте адаптер `registerSigner({ id: "iit", label, level: "qualified", hint, sign })`,
  де `sign` викликає `EndUser.SignHash` бібліотеки eusign.js і повертає `{ signatureBase64, provider: "file_key" }`.
  Бібліотеку ІІТ треба віддавати з власного сервера (CSP `script-src 'self'`).
* Внутрішній ключ АІ-СЕД ПУЕТ інтерфейс завжди позначає «не КЕП»; чи прийняти його на кроці, вирішує сервер
  (`accepted_levels` у signing-request).

## Запуск

```bash
npm ci
npm run gen:api          # типи з ../sed-app/openapi.yaml (після змін API)
npm run dev              # http://localhost:5173, /api проксіюється на SED_API_URL (типово http://127.0.0.1:8080)
npm run build            # dist/ з базою /static/
```

**Розгортання — варіант A (без окремого сервера):** sed-app сам віддає збірку:
`SED_APP_WEB_ROOT=/opt/sed/sed-frontend/dist`. Тоді `/` → `index.html`, `/static/*` → ресурси, діють CSP і заголовки
безпеки sed-app, Keycloak-клієнт `sed-web` з realm-puet.json підходить без змін. Маршрутизація на `#/…`, тож
серверу не потрібні fallback-правила.

**Варіант B (окремий контейнер):** `Dockerfile` (node → nginx-unprivileged) і `deploy/nginx.conf.template`
(той самий CSP, проксі `/api` на `SED_API_UPSTREAM`). Додайте origin інтерфейсу в `redirectUris`/`webOrigins`
клієнта `sed-web` у Keycloak. Образ у цьому середовищі **не збирався** (немає Docker-демона).

## Перевірка

```bash
npm run typecheck && npm test                     # 14 тестів: домен, CAdES/PKCS#12 з перевіркою серверним верифікатором
# наскрізні: стенд sed-app з PostgreSQL 16 + pgvector, модулями маршрутів і ключів, і цією збіркою
SED_TEST_DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost/sed_frontend_e2e python3 dev/stand.py --port 8766 &
PW_CHROMIUM=/шлях/до/chrome npx playwright test   # 3 сценарії, axe WCAG 2 A/AA без серйозних порушень
```

Наскрізні сценарії (`e2e/flow.spec.ts`): викладач реєструє службову записку → переносить реквізити → запускає маршрут →
зав. кафедри отримує внутрішній ключ і візує ним (підпис у браузері) → проректор, головбух, ректор, ПФВ підписують
→ «Погоджено», 5 чинних підписів → студент отримує «не знайдено»; проректор закріплює КЕП через виклик (файл-ключ
відкривається в браузері), відкріплює його, сервер відмовляється приймати файл-ключ як сертифікат; решта розділів,
адміністрування корпусу для ректора, вигляд на телефоні без горизонтальної прокрутки сторінки.

## Структура

| Шлях | Зміст |
|---|---|
| `src/api/` | `schema.d.ts` (згенеровано з OpenAPI), клієнт openapi-fetch з Bearer, X-Request-ID і помилками українською, виклики за модулями |
| `src/auth/` | OIDC Authorization Code + PKCE (S256) з Keycloak; токен у sessionStorage вкладки, без refresh-токена |
| `src/domain/` | чисті функції: навігація за ролями, підписи і тони статусів, форматування, реквізити, політика пароля |
| `src/kep/` | засоби підпису, PKCS#12, CAdES-BES, кодування |
| `src/components/` | доступні базові елементи: кнопки дій, поля з підказками/помилками, вкладки WAI-ARIA, діалог причини, сповіщення |
| `src/features/` | екрани: огляд, реєстр, реєстрація, картка (5 вкладок), черги, нормативна база, перевірка проєкту, ключі |
| `dev/stand.py`, `dev/fixtures/` | стенд для браузерної перевірки (фейки LLM/OCR як у тестах sed-app + ключі КЕП і внутрішній ЦСК у пам'яті); `test.p12` і `ca.pem` — ключ одноразового тестового ЦСК, лише для тестів |
| `deploy/`, `Dockerfile` | nginx-варіант розгортання |

## Безпека

| Ризик | Захід |
|---|---|
| XSS через текст з OCR/LLM | лише React-рендеринг (без `dangerouslySetInnerHTML`), CSP `script-src 'self'`, без inline-скриптів у збірці |
| Крадіжка токена | токен у sessionStorage вкладки, без refresh-токена; 401 → вихід і повторний вхід через SSO |
| Витік особистого ключа | ключ відкривається в браузері як неекспортований CryptoKey; на сервер іде лише підпис; перевірка сертифіката відмовляє файлам-ключам |
| Підпис не тієї версії | геш для підпису бере сервер (`signing-request`), не браузер; сервер звіряє його з версією |
| Одночасна правка картки | кожна дія передає `row_version`; 409 → повідомлення і перечитування картки |
| Перебір ідентифікаторів | 404 показується як «не знайдено або немає доступу» без розкриття існування |
| Кеш чутливих даних | API з `Cache-Control: no-store` (sed-app); оригінали показуються з `blob:` і звільняються при закритті |
| Помилкове рішення ШІ | жодна дія не виконується автоматично; відхилення, скасування, хибні зауваження, відкріплення ключа вимагають причини (журнал) |

## Крайні випадки

* **Модуль вимкнено на стенді** (RAG, маршрути, ключі) — пункт меню зникає, вкладка картки пояснює, чому порожня.
* **ШІ не вилучив реквізити** — форма ручного введення відкрита одразу.
* **Звіт аудиту для попередньої версії** — попередження «перевірте поточну версію повторно».
* **Критичні зауваження відкриті** — запуск маршруту лише з явною позначкою автора.
* **Виклик для закріплення прострочено** — попередження і кнопка нового виклику.
* **Строк сертифіката минув / скоро спливає** — підпис ключем з простроченим сертифікатом не надсилається; у списку ключів позначка.
* **Користувач без ролей** — банер «зверніться до адміністратора», видно лише публічні документи.
* **Слабкий пароль файлу-ключа** — підказка за тією ж політикою, що на сервері (≥ 12 символів, 3 види, без імені/пошти).

## Потрібні зміни API (для власників sed-app і модулів)

Інтерфейс працює з поточним API; ці зміни зроблять його повнішим:

1. **Нова версія документа.** Після «Повернуто на доопрацювання» автор не може завантажити виправлену версію: немає
   `POST /documents/{id}/versions`. Потрібен ендпоінт (файл → OCR → нова версія, поточна стає попередньою).
2. **Генерація проєктів наказів (пайплайн «Assistant & Generator»).** Немає API для шаблонів ДСТУ 4163 і генерації
   проєкту за коротким формулюванням, тож екрана генерації немає. Потрібні `GET /templates` і
   `POST /documents/drafts` (з маскуванням ПД перед LLM і впевненістю по полях).
3. **Аналітика затримок погодження (пайплайн «Anomaly Detection»).** Є лише `is_overdue` у черзі; для огляду
   керівника потрібен `GET /analytics/approvals` (середній час етапу, аномалії, вузькі місця за підрозділами).
4. **Назви етапів у картці.** `RouteOut.steps[]` не має `title_uk`, інтерфейс робить додатковий запит
   `GET /documents/{id}/route` (див. також sed-app README, п. 5).
5. **`accepted_levels` без `mock`.** Коли стенд дозволяє імітаційний КНЕДП, `signing-request` не включає `mock`, хоча
   сервер його приймає; інтерфейс показує тестовий ключ за прапорцем `modules.kep_mock`.
6. **Імітаційні сертифікати позначаються як «Кваліфікований (КЕП)»** у `GET /kep/keys` (рівень береться з сертифіката
   MockKnedp). Краще повертати `mock`, щоб на стенді не плутати.
7. **Нормативна база.** Немає `GET /regulations` (список актів), а `PUT /regulations/{id}/status` вимагає повний `ActIn`
   з полем `issuer`, якого немає в `SearchHit`. Потрібні список актів і `PATCH` лише статусу/строків.
8. **Адміністратор ключів** (ректор) може відкликати чужі ключі, але не має їх списку: потрібен
   `GET /kep/keys?user_id=…` для адміністратора.
9. **Імітаційний підпис** `POST /dev/steps/{id}/mock-signature` не входить в OpenAPI (експорт без dev-маршрутів),
   тож у клієнті його тип описано вручну.
10. **Синхронні виклики LLM.** Реєстрація і аудит тримають HTTP-запит хвилинами (ризик 2 sed-app); з чергою завдань
    інтерфейсу знадобиться опитування статусу або SSE.
